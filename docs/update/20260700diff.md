# Misskey 2026.6.0 → 2026.7.0 backend diff

mk-go (本リポジトリ) の upstream 追従用 diff doc。**2026.6.0 → 2026.7.0 の差分のみ** を扱う。過去分は [`20260500diff.md`](./20260500diff.md) (2026.3.2→2026.5.0)、[`20260501diff.md`](./20260501diff.md)、[`20260502diff.md`](./20260502diff.md)、[`20260504diff.md`](./20260504diff.md)、および 2026.5.4→2026.6.0 の triage [`20260622-2069-triage.md`](./20260622-2069-triage.md) を参照。

本リリースは **1.0.0 gate 対象** (1.0.0 = 2026.7.0 追従完了、方針は project memory 参照)。1.0.0 までは互換性最優先で upstream 実装に合わせる。

- 集計範囲: `misskey-dev/misskey` の `2026.6.0..2026.7.0` (stable release 2026-07-31)
- backend (`packages/backend/`) 計 99 files / +6486 / -1765、うち `src/` 52 files / +3157 / -619
- backend src/migration に触れた commit は **40 commits** (no-merges。うち約半数はログ基盤/telemetry 系の内部刷新)
- migration 3 件 (すべて additive、down あり、data loss なし)
- 取得方法: `git -C third_party/misskey fetch upstream --tags` 後、`git diff 2026.6.0..2026.7.0 -- packages/backend/`
- mk-go 該当箇所の Gap 判定は初期 grep による。設計精査は各 issue で行う

## リリース全体の性格

2026.7.0 の backend 差分は大きく 3 系統に分かれる:

1. **センシティブメディア判定の外部サービス化** (#16804 / #17570 / #17828): nsfwjs/tfjs 同梱を廃止し、公式サイドカー [sensitive-detector](https://github.com/misskey-dev/sensitive-detector) への HTTP 委譲に移行。**mk-go は #406/#751 で先行して外部化済みだが独自契約のため、公式契約への追従が必要 (1.0.0 スコープの最大項目)**
2. **セキュリティ修正 3 件** (fork merge 由来): fetch-rss の SSRF/DoS hardening、admin/reset-password と admin/unset-mfa の improper authorization、reply visibility clamp
3. **ログ基盤/telemetry の内部刷新**: 構造化ログ・JSON 出力・アクセスログ・Sentry 抽象化。wire 非依存で mk-go は slog 済みのため移植対象外

なお OTel 対応 (#17679〜#17712) は release 前の #17812 で**除去済み**。net effect は Sentry 抽象化のみ。

#### meta 新カラム (migration `1780488454126`)

```sql
ALTER TABLE "meta" ADD "sensitiveMediaDetectionApiUrl" character varying(1024);          -- NULL 可
ALTER TABLE "meta" ADD "sensitiveMediaDetectionApiKey" character varying(1024);          -- NULL 可
ALTER TABLE "meta" ADD "sensitiveMediaDetectionTimeout" integer NOT NULL DEFAULT '60000';
ALTER TABLE "meta" ADD "sensitiveMediaDetectionMaxImagesPerRequest" integer NOT NULL DEFAULT '4';
```

`admin/update-meta` の検証: timeout / maxImagesPerRequest は `type: integer, minimum: 1`。url / apiKey は `type: string, nullable: true`。

#### AiService の HTTP 契約 (公式 sensitive-detector `POST v1/detect-images`)

- URL 組み立て: `new URL('v1/detect-images', base)`。base は `sensitiveMediaDetectionApiUrl` 末尾 `/` 補正。URL parse 失敗は warn ログ + 全件 `null`
- `apiUrl` が null/空白 → 判定スキップ (全 image `null` = 非センシティブ扱い)
- リクエスト: `multipart/form-data`。各 part はフィールド名 `image{i}`、filename `{i}.png`、`type: 'image/png'` の Blob。**Content-Type ヘッダは手動設定しない** (boundary は FormData 任せ、手動指定すると boundary 欠落で読めない)
- 認証: `apiKey` 非空時のみ `Authorization: Bearer <apiKey>`
- batch: `maxImagesPerRequest` (min 1 clamp) で chunk 分割し順次送信
- レスポンス: `{success: true, result: {results: [{success: true, predictions: [{className, probability}]} | {success: false, error: {code, message}}]}}` を型ガードで厳密検証。順序はリクエスト part 順
- **エラーは全て fail-open**: HTTP 非 OK / shape 不一致 / `success: false` / 例外 → chunk 全件 `null` (= 非センシティブ扱い、warn ログのみ)。#16804 の設計判断
- **#17828: `HttpRequestService.send` を使う** (`throwErrorWhenResponseNotOk: false`)。素の fetch ではなく共通 outbound 経路 (プロキシ/UA/タイムアウト管理) を通す

#### FileInfoService の集約変更

- 画像正規化 (sharp → PNG 変換) と動画フレーム抽出 (FFmpeg) は**引き続き本体側**。detector には正規化済み PNG のみ送る
- 動画: 判定対象フレームを buffer に集め `detectSensitiveMany` で一括送信 (旧: フレームごとに個別推論)
- **成功フレーム 0 件時は集約をスキップ** (接続先未設定・通信失敗時)。旧ロジックのままだと `results.filter(...).length >= Math.ceil(0 * threshold)` が `0 >= 0` で真になり**全動画がセンシティブ化**するため、`results.length > 0` ガードを追加
- sensitive / porn のしきい値集約 (`judgePrediction`: className Porn/Sexy/Hentai の probability 判定) 自体は既存踏襲。型が `nsfwjs.PredictionType` → 自前 `Prediction` に変わったのみ

- なぜ必要: drop-in 互換。TS backend と DB (meta 列) を共有するため、コントロールパネルで設定した detector 接続情報を mk-go も読めなければ**切替時にセンシティブ判定が黙って無効化**される。逆に mk-go 独自の YAML `nsfwDetectorUrl` は TS から見えない
- **mk-go 該当箇所**: `internal/core/drive/sensitive.go` + `internal/core/drive/drive_service.go:483-501` + `internal/model/meta.go` + `internal/api/admin/handler.go`
  - mk-go は #406/#751 で外部化済みだが**独自契約** (`POST <url>` に生バイト単一 + `Content-Type: <mime>` → `{score: float64}`、しきい値は `SensitivityThreshold`)
  - meta 4 列は**存在しない** (grep 確認済)。migration 追加 + model/admin-meta/update-meta への配線が必要
  - 方針 (決定済): **公式契約を追加実装し、既存の汎用 `{score}` 契約は併存させる** (regression 回避)。meta の `sensitiveMediaDetectionApiUrl` 設定時は公式契約、YAML `nsfwDetectorUrl` のみ設定時は従来契約
  - 送信は safehttp (SSRF-safe transport) 経由にする (#17828 対応と同型)
  - fail-open 挙動 (失敗 = 非センシティブ) と動画 0 フレームガードを upstream と一致させる
  - 299×299 PNG 正規化は mk-go の `ImageProcessor` に相当処理があるか要設計 (detector 側要件: maxImageWidth/Height 299、maxBinarySize 1MB、maxParts 10)

### 2. reply visibility clamp: フォロワー限定投稿へのリプライをホーム投稿にできる問題 (SEC)

- 該当: `src/core/NoteCreateService.ts`
- 関連 PR: #17747
- 変更内容: 旧実装は「reply 先が public 以外なら `public` → `home` に落とす」のみで、**followers note への reply を home/public で作成して本文文脈を晒せた**。新実装は reply 先 visibility ごとの段階クランプ:

```ts
switch (data.reply.visibility) {
    case 'public':    break;                                        // 制限なし
    case 'home':      if (visibility === 'public') visibility = 'home'; break;
    case 'followers': if (visibility === 'public' || visibility === 'home') visibility = 'followers'; break;
    case 'specified': if (visibility !== 'specified') visibility = 'specified'; break;
}
```

- renote.localOnly / reply.localOnly の localOnly 継承は従来どおり (コード位置の整理のみ)
- なぜ必要: security (visibility escalation)。drop-in 互換でも同挙動必須
- **mk-go 該当箇所**: `internal/core/note` の create 経路の visibility 導出を要点検。mk-go が旧仕様 (public→home のみ) なら同じ穴がある。AP inbound の可視性導出 (#1560 で対応済の audience union) とは別経路なので混同しないこと

### 3. fetch-rss hardening (SEC, GHSA fork merge)

- 該当: `src/server/api/endpoints/fetch-rss.ts` (+116)
- 関連: merge commit `a12ee2e5d7` (fork 経由の security 修正)
- 変更内容:
  - **URL 検証** (`normalizeUrl`): 空/8192 字超 → `INVALID_URL`。URL parse 失敗 → 同。`http:`/`https:` 以外の scheme、userinfo (`username`/`password`) 付き → 同。hash は除去して正規化
  - **リダイレクト先の再検証**: fetch 後 `res.url` の protocol が http(s) 以外なら throw
  - **レスポンスサイズ上限**: `size: 1MiB` を `httpRequestService.send` に指定
  - **同時実行制御**: 同一 URL の in-flight request は Promise を共有 (dedup)。全体で 32 並行超 → `FETCH_RSS_UNAVAILABLE` (503)
  - **rate limit**: `duration 60s, max 300`
  - 新 error (meta.errors):
    - `INVALID_URL` id `89b7ee05-ccfc-4bdd-9b13-61172fd1e06c` (400)
    - `FETCH_RSS_FAILED` id `8db5d3d8-31d7-452f-b0cc-ca3b8925de12` (422, kind server)
    - `FETCH_RSS_UNAVAILABLE` id `91e6ff44-c63f-4725-9ad0-b7a40d7f7655` (503, kind server)
  - fetch/parse 失敗は一律 `FETCH_RSS_FAILED` に丸める
- なぜ必要: security (SSRF 面の縮小 + 外部 RSS fetch を踏み台にした DoS 対策) + error shape の drop-in 互換
- **mk-go 該当箇所**: `internal/api/fetchrss/handler.go`。mk-go は safehttp 経由のため SSRF 面は既に狭いが、(1) URL 長/userinfo/scheme 検証、(2) 1MiB サイズ上限、(3) 同一 URL dedup + 32 並行上限、(4) 3 error の code/id/status、(5) rate limit 300/min の 5 点を upstream に揃える
