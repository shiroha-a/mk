## 移植優先度: 高 (動作 / 連合互換性に影響)

### ActivityPub: relay-actor 由来 Announce でも lock を取得

- 該当: `core/activitypub/ApInboxService.ts` (`announceNote`)
- 変更内容: lock 取得時の key を `uri` (= 元 note の URI) ではなく `getApId(activity)` (= Announce activity 自体の ID) に変更。relay actor 由来 Announce で「同一 note を 2 つの relay 経由で受信」する際、key が同じになって race するのを防ぐ。
- なぜ必要: 2026.5.0 で導入されたリレー由来 Announce 処理 (#17308) と組み合わせて、同 activity の重複処理を排除するために必要。
- 関連 PR: misskey-dev/misskey#17356
- mk-go 該当箇所: `internal/core/federation/processor.go` の `handleAnnounce` (= `act.ID` を使った重複 check は既にあるが、lock 取得を URI ベースから activity.ID ベースに揃える必要があるか要確認)

```ts
// before
const unlock = await acquireApObjectLock(this.redisClient, uri);
// after
const activityUri = getApId(activity);
const unlock = await acquireApObjectLock(this.redisClient, activityUri);
```

### Notification: followers-only note の通知漏れ修正

- 該当: `core/NoteCreateService.ts` (`NotificationManager`)
- 変更内容: `visibility === 'followers'` の case が **コメントアウトされていた** (= visibleUserIds が default の空集合になり、follower 全員に通知されない)。コメント解除して `visibleUserIds = null` (= 全員フィルタ無し) を設定する。
- なぜ必要: フォロワー限定 note を投稿しても、メンション通知が follower に届かない bug。具体的には specified visibility と同じ「named user list」処理で followers-only も扱おうとしていた残骸が残っていた。
- 関連 PR: misskey-dev/misskey#17363
- mk-go 該当箇所: `internal/core/note/note_create_service.go` または `internal/core/notification/hooks.go` の通知配信経路。**followers-only note の処理が specified と分かれているか要点検**。

```ts
// before (=コメントアウトされ default の Set() = 空 へ落ちていた)
// case 'followers': {
//     visibleUserIds = new Set(followers.map(f => f.followerId));
//     break;
// }
// after
case 'followers': {
    visibleUserIds = null; // フィルタなし = 全員に通知
    break;
}
```

### Notification: ULID 環境で notificationTimeline XADD 失敗 → 通知 ~10s 遅延

- 該当: `core/NotificationService.ts` (`toXListId`)
- 変更内容: Redis Stream の sequence ID (= `<unix_ms>-<seq>` 形式) で `seq` 部分が unsigned 64-bit でなければならないが、ULID の additional 部分が 64-bit 上限を超えるケースがあって XADD が失敗していた。`BigInt.asUintN(64, additional)` で下位 64-bit に切り詰める。
- なぜ必要: mk-go の既定 ID は aidx だが、`MK_ID=ulid` を選択したインスタンスで通知遅延が発生する。
- 関連 PR: misskey-dev/misskey#17358
- mk-go 該当箇所: `internal/stream/notification_publisher.go` (もしくは `internal/queue/processors/` の通知 publisher) で Redis XADD の sequence 生成箇所。**ULID 経路で同 bug があるか要確認**、aidx 経路は問題ない可能性が高い。

```ts
// before
return date.toString() + '-' + additional.toString();
// after
// Redis Stream sequenceは unit64 制約があるため、収まらない場合は下位 64bit を取る
return date.toString() + '-' + BigInt.asUintN(64, additional).toString();
```

- 変更内容: チャンネル作成権限を role policy で制御できるように。default は true なので既存環境への影響はないが、**admin が role で false に設定すると channels/create が拒否される**。
- 関連 PR: misskey-dev/misskey#17121
- mk-go 該当箇所:

