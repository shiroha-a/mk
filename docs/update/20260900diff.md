### 2. `.well-known/change-password` (実装する)

- upstream: `04600982f0` `feat(backend): Add support of ".well-known/change-password" (#17901)`
- 該当: `src/server/WellKnownServerService.ts` (TODO コメントの有効化、実質 4 行)

```ts
fastify.get('/.well-known/change-password', async (request, reply) => {
    const redirectUri = new URL('/settings/security', this.config.url);
    reply.redirect(redirectUri.toString(), 302);
});
```

[W3C: A Well-Known URL for Changing Passwords](https://w3c.github.io/webappsec-change-password-url/) の仕様で、パスワードマネージャ (iCloud キーチェーン / 1Password / Chrome) が「パスワードを変更」の遷移先を機械的に見つけるために使う。認証は不要。

**mk-go: 未対応 → #2877 で実装済み。**

mk-go の well-known は GET 5 本 (`webfinger` / `host-meta` / `host-meta.json` / `nodeinfo` / `oauth-authorization-server`) + `OPTIONS /.well-known/*` の計 6 登録で、**`change-password` だけが差分**。

**現状は 404 でも SPA fallback でもなく 405 Method Not Allowed が返る。** `OPTIONS /.well-known/*` のワイルドカードがあるため、Echo は path 一致・method 不一致のノードで止まり `GET /*` の catchall へ戻らない (echo v4.15.3 で実測: `Allow: OPTIONS`、body は `{"message":"Method Not Allowed"}`)。**OPTIONS を外すと 200 + index.html になる**ので、挙動はこのワイルドカードに依存している。いずれにせよパスワードマネージャは 302 を得られない。

実装方針:
- `internal/api/wellknown/handler.go` に `ChangePassword` を追加。`Handler` は既に `origin` を持つので `c.Redirect(http.StatusFound, ...)` で足りる
- `router.go` の well-known ブロック (SPA catchall より前) に登録する
- **`federationDisabled()` は通さない** — upstream が 403 にするのは host-meta / host-meta.json / nodeinfo / webfinger の 4 本で、`oauth-authorization-server` と `change-password` は対象外 (mk-go 側も同じ 4 本)
- リダイレクト先 `/settings/security` は fork frontend に `pages/settings/security.vue` として実在する
- **絶対 URL か相対パスかは要判断。** upstream は `config.url` 基準の絶対 URL

**難易度: S。**

### 依存更新 (影響なし)

- upstream: `04fd954f0e` `deps: update dependencies (major) (#17857)`

backend の実コード変更は 3 ファイルのみ。

- `config.ts` — `RedisOptions` の TS 型分解のみ。YAML キーの増減なし

**mk-go: 影響なし。** `state` の enum 検証をそもそも行っておらず (任意の文字列を受けて `default:` で pending にフォールバックする既存の緩さ)、`paused` は明示的に空返しなので upstream v6 と結果的に一致する。`counts` の shape も `active / delayed / waiting / completed / failed` の 5 キーで `paused` を含まない。

**mkq の pause セマンティクスは v5 のまま**だが、drop-in の wire 互換は壊れない。bullmq v6 は pause 時に `HSET meta paused 1` するだけで `wait` → `paused` の RENAME をしなくなった一方、resume 側に legacy paused key を `wait` へ戻す互換処理が残っている。mkq は RENAME 方式だが双方とも `meta.paused` を真とみなすので、同じ Redis を共有しても pause は相互に効く。mk-go が pause 中に積んだジョブも resume で `wait` へ戻る (**ただし v6 の resume は 1 回あたり最大 7000 件**なので、それを超える場合は resume を複数回必要とする)。

**`state` の enum 検証そのものは追随していない。** upstream は `paramDef.state` から `'paused'` を外したので `{"state":["paused"]}` が 400 になるが、mk-go は enum 検証を持たず (任意の文字列を `default:` で pending にフォールバックする既存の緩さ)、`paused` は明示的に空返しなので 200 `[]` を返す。同じ入力でレスポンスが分岐する箇所として残る。

### `notes/reactions` の可視性 (SEC, fork merge)

- upstream: `cb7c30d5a2`。可視性チェックが無く、見えないノートのリアクションが読めていた。`allowGet: true` / `cacheSec: 60` も削除された (キャッシュ経由でも漏れるため)。**mk-go は `GET /notes/reactions` を残している**が、`/api` 全体に `Cache-Control: private, max-age=0, must-revalidate` が効くのでキャッシュの問題は生じない (GET variant は `docs/divergence.md` に既記載)

**mk-go は最初から gate 済み。** `internal/core/reaction/reaction_service.go` の `List` が viewer を受け取り `CanSeeNote` gate を掛けて `ErrNoteNotVisible` を返す。実装コメントに「upstream は返すが mk-go は 404 NO_SUCH_NOTE を返す」と明記されている。

### メール HTML のインジェクション (SEC, fork merge)

- upstream: `48ffed3ede`。`EmailService` のテンプレートが subject / html / logoImageUrl などを素で埋め込んでいた (`// TODO: htmlサニタイズ` が残っていた)

**mk-go は先行対策済み。** `internal/core/email/wrapper.go` の `WrapHTML` が埋め込む値をすべて `html.EscapeString` する。`BodyHTML` だけは caller 責任だが、本番の呼び出し 4 箇所すべてが escape 済みの helper 出力を渡している。SMTP ヘッダ側も `internal/misc/smtp/smtp.go` の `sanitizeHeaderValue` が CR/LF を落とし、boundary は `crypto/rand` 由来。

なお upstream の `NotificationService` 側 (フォロー通知メールの `${follower.name}` 未エスケープ) は**ブロックコメント内の死んだコード**で、修正後もコメントのまま。mk-go にはフォロー通知メールの送信自体が無い。

### WebAuthn challenge の名前空間分離 (SEC, fork merge)

- upstream: `c302269b0d`。登録 / 2FA 認証 / passkey サインインが同一の `webauthn:challenge:` 名前空間を共有し、しかも passkey の `context` が**リクエストボディ由来**で `typeof === 'string'` しか見ていなかった

**mk-go は #698 / #705 の時点で分離済み。** `internal/core/twofactor/webauthn.go` のキーは `twofa:webauthn:<userID>:login` / `:registration` / `twofa:webauthn:passkey:<ctxID>` の 3 系統。**context はどちらもサーバ生成**なので (upstream は `randomUUID()`、mk-go の `newPasskeyContext()` は `crypto/rand` 16 バイト → 32 文字 hex) そこに差は無い。**効いているのはキーの形** — upstream は `webauthn:challenge:${context}` が userId 名前空間と同形で衝突しえたのに対し、mk-go は固定リテラル `passkey:` が可変部の**前**に来るため構造的に衝突しない (userID は base36 で `:` を含まない)。

残る差分は「context の形式検証が無い」点だけだが、到達先は自分の passkey セッションの GETDEL 一発で、他フローのキーには構造上当たらず、128bit の乱数は推測できない。多層防御として入れるなら 1 行 (難易度 S、優先度低)。

### 衝突面は 2 ファイルだけ

upstream が触った 81 ファイルと fork が触った 47 ファイルの積集合:

```
$ git diff --name-only 2026.7.0..2026.9.0  -- packages/frontend{,-shared,-embed}/ packages/misskey-js/ packages/sw/ locales/ | sort > up
$ git diff --name-only 2026.7.0..bcc3f260  -- (同上) | sort > fk
$ comm -12 up fk
locales/ja-JP.yml
packages/frontend/src/pages/admin/job-queue.vue
```

- **`packages/frontend/src/pages/admin/job-queue.vue`** — upstream は **Paused タブを削除**し `jobState` の型を
  `Misskey.entities.AdminQueueJobsRequest['state'][number]` (misskey-js の autogen) に変えた。
  fork 側は mk-go 独自の `runtime` ブロック (Workers 表示) を足し、`tab` の型に依存する
  キャストを入れている。**両方が同じ型定義の周辺を触るので手で解く必要がある**
- **`locales/ja-JP.yml`** — upstream +2 行に対し fork +40 行。どちらも追加のみなので、
  同じ位置に足していなければ機械的に解ける

50 コミットを cherry-pick する割に衝突面が狭いのは、fork の独自変更が
mk-go 固有ページ (プラグイン管理 / 承認制サインアップ / mk-go 独自ダッシュボード) に
集中していて、upstream が今回触った領域 (MkLightbox / 通知トースト / ワードミュート /
audio visualizer) と重ならないため。

### misskey-js

autogen 型の差分は **backend の 3 項目の反映のみ**で、独自の変更は無い。

- `admin/queue/stats` の permission が `read:admin:emoji` → `read:admin:queue`

mk-go は misskey-js を wire 契約の参照に使っているので、**submodule bump 時に
