# プラグイン peer プロトコル

mk-go 同士でだけ通じる、署名付きの HTTP チャネルの仕様 (#2537)。プラグインが
他のインスタンスの**同じプラグイン**とやりとりするために使う。

書き方は [プラグイン作者向け](plugins/authoring.md#他のインスタンスとやりとりする)
にある。こちらは wire の形を固定するための文書で、**実装を変えたらここも直す**。

## 適用範囲

**本体の機能はこのチャネルに載せない。** これは好みではなく、drop-in が成立する
条件そのもの。

プラグインは mk-go にビルド時に組み込まれるので、TS Misskey へ切り替えれば
プラグインごと消える。**チャネルに載っているものがプラグインのデータだけなら、
切り替えで失われるのはプラグインの分だけ**で、AP 側には何も残らない。この代金は
プラグインを持った時点で既に払っている。

本体が 1 つでもここに載せると、その性質が崩れる。切り替えた側は
`signup_application` のように自分の DB を畳めばよいが、**相手のサーバーの状態に
依存する機能は片付け方が無い**。

載せてよいかの判定は 1 つ。**相手が TS Misskey だったとき、その機能は「劣化」
するのか「消える」のか。** 消えると困るものは AP に載せるか、そもそも作らない。

## 経路

| | |
|---|---|
| メソッド | `POST` |
| URL | `https://<host>/api/plugin/<プラグイン名>/_peer` |
| Content-Type | `application/json` |

`_` で始まるパスは mk-go の予約で、プラグインからは登録できない (受け口を奪えない
ようにするため)。

受け口が存在するのは、相手がそのプラグインを**組み込んでいて、設定で有効で、
`Peered` を宣言していて、`Routes` を持っていて、そのプロセスが HTTP を提供して
いる**ときだけ。`Routes` まで要るのは現状の実装の都合で、後述の乖離の原因でもある。
どれか欠けたときに何が返るかは[応答](#応答)を見ること。

## 要求

```json
{ "id": "<相関 ID>", "payload": <不透明> }
```

- `id` は**送信側の mk-go が振る** (インスタンスの ID 生成器。既定は aidx だが
  設定で変わる)。プラグインは payload に自前の ID を埋めなくてよい。`Send` の
  戻り値と同じ値で、相手の応答を受け取るときに `OnReply` の `id` として渡る
- **受信側のハンドラに `id` は渡らない。** `Handle` が受け取るのは `from` と
  `payload` だけ。配送は再送があるので at-least-once だが、**受信側は同じ交換を
  識別できない**。冪等にする必要があるなら payload に自前の ID を入れること
- `payload` の中身は mk-go が**解釈しない**。ただし要求全体は `/api` 共通の
  JSON パーサを通るので、JSON として妥当であることと、`__proto__` /
  `constructor.prototype` を持つオブジェクトを含まないことは要る (Fastify の
  secure-json-parse 互換)。反すると `400` になり、ハンドラまで届かない。
  それ以外の**形の互換はプラグインの責任**

## 応答

| 状況 | 応答 |
|---|---|
| ハンドラが値を返した | `200` + その値を JSON にしたもの |
| ハンドラが `nil` を返した | `204` (本文なし) |
| 失敗 | 4xx / 5xx。本文は下表 |

**エラーの `message` にプラグインの文面は載らない。** ハンドラが返したエラーは
ログにだけ残す (DB のエラー等の内部事情が相手のサーバーに漏れるため)。

受信側が返す status:

| status | 意味 | 本文 |
|---|---|---|
| `400` | 本文が空 / JSON として壊れている / proto poisoning | `{"statusCode":400,"code":"FST_ERR_CTP_..."}` |
| `400` | 署名は通ったが、本文をエンベロープとして読めない | `{"error":{"message":"..."}}` |
| `401` | 署名を検証できない | `{"error":{"message":"..."}}` |
| `403` | 送信元をブロックしている / 連合の許可設定の対象外 | `{"error":{"message":"..."}}` |
| `413` | 本文が上限を超えている | `{"message":"Request Entity Too Large"}` |
| `500` | プラグインのハンドラがエラーを返した | `{"error":{"message":"..."}}` |
| `501` | 受け口はあるが `Handle` を呼んでいない | `{"error":{"message":"..."}}` |

**本文の形が 2 通りあるのは、前段の共通ミドルウェアが返す分があるため。**
最初の `400` (`/api` の JSON パーサ) と `413` (body limit) はプラグインの受け口に
届く前に返るので、`{"error":{"message":...}}` ではなく Fastify 互換 / echo 既定の
形になる。**受信側の実装が mk-go でないなら、この 2 つも
`{"error":{"message":...}}` で構わない** — 送信側は status しか見ない。

### 受け口が無いときは `200` + `{}` が返る (既知の乖離)

`/api` の catchall が未登録パスの非 GET に `200` + 空オブジェクトを返すため
(upstream 未実装エンドポイントで公式フロントが例外を投げるのを避けるための
pass-through)、**受け口が無いことと「プラグインが空のオブジェクトを返した」が
区別できない**。到達するのは 2 通り:

- 相手が `Peered: true` を宣言しているが `Routes` を持たない。受け口は
  `Routes != nil` の内側でしか張られないのに、nodeinfo の広告は `Routes` を
  見ないので、**宣言はするのに受け口が永久に無い**
- 相手が nodeinfo の肯定キャッシュ (6 時間) の途中でプラグインを外した

`{}` は 0 バイトではないので、`OnReply` が**偽の応答で呼ばれる**。プロトコルとしては
受け口が無いと分かる応答 (`404`) を返すのが正しく、mk-go 側の修正は #2822。
それまでは、応答が空オブジェクトかどうかをプラグイン側で見分けること。

## `OnReply` は同じ HTTP 応答で駆動される

**別のリクエストで返ってくるわけではない。** `Send` は goroutine を起こして
POST し、**その HTTP 応答の本文**を `OnReply` に渡す。API の形が非同期に見えるが、
やりとりは 1 往復の同期 RPC。

したがって:

- 応答が空 (`204` / 本文 0 バイト) なら `OnReply` は**呼ばれない**
- 相手が `Send` を呼び返す必要は無い。呼び返せば、それは別の交換になる
- 相手の処理が長いと、こちらの 1 試行 (15 秒) を使い切って失敗になる

## 署名

送信側は AP の deliver と同じ形で署名する。

- 鍵: インスタンスアクターの秘密鍵
- 署名対象: `(request-target)` / `date` / `host` / `digest`
- `Digest` は本文の SHA-256

受信側は inbox と同じ受け入れ判定を通す。**`from` は名乗りではない** —
`Host` ヘッダや payload の中身ではなく、署名した鍵の持ち主から確定する。

- `(request-target)` / `date` / `host` / `digest` が署名対象に入っていること
- `Date` が現在時刻から **5 分**以内であること。`X-Date` があればそちらを見る。
  読めない書式と空は通す (upstream の parser に合わせた緩さ)
- `Host` が**受信側の設定ホストと一致**すること。別名ドメイン宛には送れない
- `Digest` が本文の SHA-256 と一致すること
- keyId から actor を解決し、その公開鍵で検証できること
- 解決した actor がリモートであること (ローカルユーザーの鍵では通らない)

`Date` と `Host` は送信側への要求でもある。**時計が 5 分以上ずれていると送れない。**

確定したホストは `normalizePeerHost` を通す。scheme を剥がして小文字にし、
**LDH ラベル + 任意のポート**の形でなければ拒否する。`example.test@10.0.0.1`
のような値が URL に連結されて userinfo として解釈されるのを防ぐ。

## 上限と時間

| | 値 | 備考 |
|---|---|---|
| 要求の本文 | プラグインが宣言 (既定 64 KiB) | 下の節を見ること。**要求と応答の両方に同じ値**が掛かる |
| 応答の本文 | 同上 | 超えた応答は**切り詰めずエラー**にする (`OnReply` は呼ばれない) |
| 1 試行 | 15 秒 | `OnReply` に渡す ctx も同じ 15 秒 |
| nodeinfo の取得 | 10 秒 | 文書は 256 KiB まで |
| 再送 | 初回 + 2 秒 / 10 秒 / 60 秒の計 4 回 | **プロセス内で完結する。再起動をまたがない** (#2819 で変更予定) |

送信が最後まで失敗しても、**プラグインには通知されない** (`OnReply` が呼ばれない
だけ)。運営者が追えるよう warn ログには残る。`OnReply` が返したエラーも同じく
warn ログ止まりで、再送はしない。

**`Send` が即座に返るとは限らない。** nodeinfo がキャッシュに無いと、`Send` は
呼び出し元の goroutine で取得を待つ (最大 10 秒)。POST 自体は goroutine に逃がす
ので相手の遅さは伝播しないが、**プラグインの HTTP ハンドラの中で呼ぶなら、初回だけ
詰まりうる**ことを見込むこと。

**レート制限は無い。** 本体の per-endpoint テーブルは `/api/plugin/...` を持たない
ので、受け口にも送信側にも上限は掛からない。必要ならプラグインが自前で持つこと。

### 本文の上限はプラグインが決める

インスタンス全体で 1 つの定数にすると、**一番大きなプラグインに全体が引きずられる**。
`Definition.PeerMaxBody` で宣言し、宣言が無ければ **64 KiB** (AP inbox と同じ)。

- **測るのはエンベロープ込みの本文。** payload に使えるのはここから相関 ID の分
  (aidx なら 36 バイト) を引いた残り。送信側もエンベロープで測るので、境界が
  ずれて「送信側を通って相手で `413`」にはならない
- **プラグインが単独で宣言できるのは既定値まで。** それを超える宣言は運営者が
  `plugins.<名前>.peerMaxBody` で許可したときだけ有効になり、許可が無ければ
  既定値に丸めて起動時に warn を出す。**プラグインを 1 つ足しただけで
  インスタンスの露出が広がらない**ようにするため
- 運営者の設定も 1 MiB (`/api` 全体の body limit) で頭打ち
- 判定は**読む前**に行う。受け口は署名を検証する前に本文を読み終えている
  (`auth.Authenticate` が token 抽出のため読む) ので、上限は handler ではなく
  global の `BodyLimitByPath` に掛けてある

## 送る前の検査

`Send` は goroutine に逃がす前に全部済ませる。**送ってから失敗を知る形にすると、ブロックして
いる相手にも一度は接続してしまう。**

表の順が実装の判定順。

| | 拒否する条件 |
|---|---|
| 宣言 | `Definition.Peered` を立てていない |
| 宛先の形 | `normalizePeerHost` を通らない |
| 自分自身 | 宛先が自ホスト |
| ブロック | `IsBlocked(host)` または `!IsAllowed(host)` (連合の許可設定) |
| 相手の能力 | 相手の nodeinfo にこのプラグインの宣言が無い |
| 大きさ | エンベロープ込みの本文がこのプラグインの上限を超える |

SSRF そのものは outbound が safehttp なので塞がっている。宛先の形を見るのは、
**意図しない公開ホストへ署名付きのリクエストを送ってしまう**ことを防ぐため。

## 相手が持っているかの判定

`https://<host>/nodeinfo/2.1` を引き、`metadata.mkGoPlugins` にプラグイン名が
あるかを見る。

- `Peered: true` を宣言し、**かつ設定で有効になっている**プラグインだけが名前を
  出す。宣言していないものは名前も出ない (入れている拡張を全部晒さないため)
- 相手が mk-go でなければこのキーは無いので、`Send` はそこで止まる
- キャッシュの寿命は**名前が 1 つでもあれば 6 時間、空なら 30 分**。
  「自分のプラグインがあるか」ではないので、**相手が別の peered プラグインを
  持っていて自分のだけ無い場合は 6 時間側**になる
- **取得の失敗は覚えない。** 一時的な不調で「持っていない」と決めつけると、
  相手が復帰しても寿命の間ずっと送れなくなる

## 版

**エンベロープに版は無い。** 本体機能を載せない限り、両端は同じプラグインを
持っている前提なので、形の互換はプラグイン側の payload の問題になる。

本体機能を載せる、プラグイン以外のパス空間を切る、`mkGoPlugins` とは別の能力
広告を足す — このいずれかが必要になったら、**先にエンベロープの版を決めること**。
インスタンスをまたぐ契約なので、`plugin.APIVersion` (同じバイナリの中を見る
ビルド時の検査) では表現できない。
